# Eval Metrics Dashboard — Review Guide

_Covers the 📐 Eval Metrics tab in Eval Measurements. Explains how the three filters work, which sections respond to each filter, and known limitations._

_Last updated: 2026-05-30_

---

## Dashboard Overview

The Eval Metrics tab shows 56 metrics across 9 sections. Metrics are sourced from two different tables in ClickHouse:

| Source table | What it contains | Examples |
|---|---|---|
| `otel.otel_traces` | Raw span data — durations, status codes, span attributes, token counts from LLM spans | Latency, Cost, Tool Calls, Handoff Rate |
| `otel.eval_scores` | LLM judge scores written by the eval runner after each trace | Faithfulness, Relevance, Instruction Following, Hallucination |

This distinction is the key to understanding how filters behave.

---

## The Three Filters

### Source (`all` / `production` / `benchmark` / `exploratory`)

Filters traces by `SpanAttributes['trace.source']` — the origin of the trace:

- **`production`** — live agent calls from the Chat UI
- **`benchmark`** — traces generated by eval runner test suites
- **`exploratory`** — ad-hoc or development runs

**This is the most effective filter.** It applies to both `otel_traces` queries and `eval_scores` queries, so every section responds to it.

### Agent (`orchestrator` / `searcher` / `summarizer` / `translator`)

Filters to traces where the selected agent participated.

**Current implementation (Option A — trace-level):** Finds trace IDs in `prompt_evals` where `agent_name = 'searcher'`, then filters `eval_scores` to those traces, and filters `otel_traces` to traces with a matching `SpanAttributes['agent.role']` span.

**Known limitation:** In the multi-agent orchestrator setup, every trace contains all agents as sub-spans. Filtering by `searcher` returns almost every trace because the searcher participates in nearly all orchestrator runs. As a result, metric values change very little when switching between agents.

See the [Known Limitations](#known-limitations) section below.

### Model (`gpt-4o-mini` / `ollama_chat/gemma4:26b` / etc.)

Filters to traces where the selected model was used, resolved via `prompt_evals.model`.

Same trace-level limitation applies — a trace that used `gemma4:26b` for one agent and `gpt-4o-mini` for another would be included when filtering for either model.

## How to Interpret Results Correctly

### For agent comparison
Use the **Source filter** to narrow to `production` first — this removes benchmark/eval noise and gives you a clean baseline. Then use the **time window** (top of the page) to compare before/after a model or agent change.

Direct agent-to-agent comparison in the Eval Metrics tab is best done via the **Prompt Analysis tab** (same page), which lets you filter by `agent_name` and see per-trace scores side-by-side.

### For model comparison
The most reliable model comparison uses **Prompt Analysis** → filter by model → look at `avg latency`, `total tokens`, and individual eval scores per trace.

### For cost tracking
Cost per Task in Section 2 shows the **average cost per trace** across all agents combined. For per-agent cost breakdown, use the **EvalGov Agent** — ask `"show me cost breakdown by agent"` or check the **AI Governance → Token Budgets** page which shows today's cost per agent.

## Known Limitations

### 1. Agent / Model filters have limited effect on span-based metrics

**Root cause:** In the multi-agent orchestrator setup, a single trace contains spans from all agents (orchestrator, searcher, summarizer, translator). Filtering at the trace level by agent returns almost all traces. Metrics like Cost per Task and E2E Latency cover the full trace, not just the selected agent's slice.

**What a proper fix requires (Option B — span-level filtering):**

| Metric group | Complexity | Effort | Approach |
|---|---|---|---|
| Latency, Success Rate, Failure Rate, Timeout | 🟢 Easy | ~10 min | Add `AND SpanAttributes['agent.role'] = 'X'` directly to `agent.task` span queries — filter condition already exists on the span |
| TTFT, Token Usage, Cost (model filter) | 🟡 Moderate | ~10 min | Add `AND SpanAttributes['gen_ai.request.model'] LIKE '%X%'` to LLM span queries — model name is already in the span attribute |
| Cost, Token Usage (agent filter) | 🔴 Complex | ~45-60 min | LLM spans don't carry `agent.role` — must walk the ParentSpanId chain from each LLM span up to its owning `agent.task` span to attribute tokens/cost per agent. This is the same logic `eval_pipeline.py` implements in Python (nearest task ancestor walk) but must be expressed as ClickHouse SQL using a self-join or array join on span parent relationships. |

**Implementation plan when ready:**

**Step 1 — Easy wins (agent filter on latency/reliability metrics):**
- In `_em_ft()`, add a span-level agent condition: `AND SpanAttributes['agent.role'] = '{em_sel_agent}'` for queries that already target `SpanName = 'agent.task'`
- Queries affected: ev[1], ev[8], ev[11], ev[37], ev[42]
- No new joins needed — just an extra WHERE condition

**Step 2 — Moderate (model filter on cost/token metrics):**
- Add a model condition to the `_em_LLM` filter block: `AND SpanAttributes['gen_ai.request.model'] LIKE '%{em_sel_model}%'`
- Queries affected: ev[9] Cost, ev[10] TTFT, ev[12] Token Usage
- Straightforward since model is already a span attribute on LLM spans

**Step 3 — Complex (agent filter on cost/token metrics):**
- Requires a ClickHouse subquery that: (a) selects all `agent.task` SpanIds for the target agent, (b) joins LLM spans on ParentSpanId to attribute them to the owning task span
- Example structure:
  ```sql
  -- Find LLM spans whose immediate parent is a task span owned by 'searcher'
  SELECT sum(tokens) FROM otel.otel_traces llm
  INNER JOIN (
      SELECT SpanId FROM otel.otel_traces
      WHERE SpanName = 'agent.task'
        AND SpanAttributes['agent.role'] = 'searcher'
  ) task ON llm.ParentSpanId = task.SpanId
  WHERE llm.SpanName IN ('openai.chat', 'call_llm', ...)
  ```
- Note: this only works for direct parent attribution. Deeper nesting (LLM span → intermediate span → task span) requires recursive traversal not natively supported in ClickHouse, making this the hardest piece.

### 2. Some metrics marked "Needs instrumentation"
Metrics showing `—` (Subtask Completion, False Refusal Rate, Idle Agent Time, etc.) require additional span attributes that are not currently emitted. These are placeholders for future instrumentation.

### 3. Multi-turn conversation metrics (Section 9)
Knowledge Retention, Role Adherence, Conversation Completeness, and Conversation Relevancy only populate for traces evaluated by the `multiturn_judge` evaluator. These will be empty for single-turn production traces.

## Quick Reference — Where to Find What

| Question | Where to look |
|---|---|
| How is faithfulness trending by agent? | Eval Metrics tab → Section 1, filter by Source=production |
| What did each agent cost today? | AI Governance → Token Budgets, or ask EvalGov Agent |
| Which traces had the worst scores? | Prompt Analysis tab → sort by metric |
| What did a specific user ask? | Prompt Analysis tab → search by trace ID or conversation ID |
| How does gpt-4o-mini compare to gemma on relevance? | Prompt Analysis tab → filter by model, compare avg scores |
| Is the searcher causing latency issues? | EvalGov Agent → "show me latency by agent for the last 7 days" |
